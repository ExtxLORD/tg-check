# 📬 mail-read-bot — read-only бот «почта → Telegram»

Маленький бот, который **читает непрочитанные письма** с вашего ящика и **пересылает их вам в Telegram** (текст + вложения). Больше он ничего не умеет — и это заложено в архитектуру, а не в настройках.

## Гарантии read-only

| Действие | Возможность |
|---|---|
| Читать письма (`IMAP SEARCH UNSEEN` + `FETCH BODY.PEEK[]`) | ✅ единственное чтение |
| Отправить письмо кому-либо | ❌ **SMTP в коде физически отсутствует** |
| Удалить / переместить письмо | ❌ нет `DELETE`, `EXPUNGE`, `MOVE` |
| Изменить письмо | ❌ нет |
| Пометить «прочитано» (`STORE +FLAGS \Seen`) | ⚠️ **только** после успешной отправки вам в Telegram — иначе письмо ушло бы повторно |
| Отправлять сообщения в Telegram | ✅ только в ваш `TG_CHAT_ID`; чужие чаты игнорируются (кнопки — то же самое: текст в ваш чат) |

`BODY.PEEK[]` специально не ставит флаг `\Seen` при чтении — письмо становится «прочитанным» ровно в момент, когда текст и вложения уже дошли до вас.

## Что делает

1. Фоновая проверка каждые `CHECK_INTERVAL` секунд (по умолчанию 5 минут) + сразу при старте.
2. Кнопки **под полем ввода** (обычная клавиатура Telegram): 🔍 Проверить сейчас · 📊 Статус · ❓ Помощь — нажимать не надо ничего писать. Чтобы они появились, отправьте боту `/start` один раз (клавиатура остаётся в чате навсегда, `is_persistent`). Команды `/check`, `/status`, `/help` работают ровно так же и продублированы в меню «/» рядом с полем ввода (`setMyCommands`).
3. Для каждого непрочитанного: шлёт в чат шапку (От, Тема, Дата) + весь текст (HTML конвертируется в текст), затем каждое вложение отдельным документом → помечает прочитанным.
4. Лимит `MAX_PER_CHECK` (25) за раз — чтобы при большом backlog не получить тысячу сообщений разом; остаток дойдёт следующими проверками.
5. Вложения > `MAX_ATTACHMENT_MB` (50 МБ — потолок Bot API) не отправляются, вместо них придёт уведомление.

## Установка (≈3 минуты)

```bash
cd mail_read_bot
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# отредактируйте .env
python bot.py
```

### 1. Токен бота
Откройте в Telegram → **@BotFather** → `/newbot` → придумайте имя и юзернейм → получите токен вида `123456:ABC-DEF...`. Вставьте в `TG_BOT_TOKEN`.

### 2. Ваш chat_id
1. Напишите своему боту любое сообщение (например `/start`).
2. Откройте в браузере: `https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates`
3. В JSON найдите `"chat":{"id": 123456789}` — это `TG_CHAT_ID`.

### 3. Почта @fa.ru
Заполните `MAIL_LOGIN` и `MAIL_PASSWORD`. По результатам разведки:

- Вероятный IMAP-сервер: **`mx.fa.ru:993`** (DNS: `mx.fa.ru → 217.173.73.212`, у сайта wildcard `*.fa.ru`).
- Если не подключается — посмотрите «входящий сервер (IMAP)» в настройках своего почтового клиента/OWA или спросите админа. Возможные кандидаты: `mx.fa.ru`, `fa.ru`.
- Если включена двухфакторная авторизация — используйте **пароль приложения**, а не основной пароль.
- Корпоративная почта на Exchange/Microsoft 365 может иметь отключённый IMAP — тогда попросите администратора его включить.

## Проверка

```text
Запустите python bot.py
→ в Telegram придёт приветствие-статус запуска, затем письма (если есть непрочитанные)
→ /check  — ручная проверка
→ /status — когда была последняя проверка и что нашла
```

Логи пишутся в консоль (пароль в логи не попадает).

## Деплой на свой VPS (рекомендуется) 

Боту не нужны входящие порты — только исходящие (Telegram :443, IMAP :993). На VPS с уже работающим VPN ничего в фаерволе менять не нужно. Ресурсы: ~50–80 МБ RAM, ≈0% CPU.

От рута на сервере (Ubuntu/Debian):

```bash
git clone https://github.com/ExtxLORD/tg-check.git /opt/mail-read-bot
cd /opt/mail-read-bot
bash deploy/install.sh
```

Скрипт создаст изолированного пользователя `mailbot`, venv, `.env` (шаблон — **заполните вручную** пароль почты и токены) и включит systemd-юнит `mailbot.service` с автозапуском.

**Важно для VPS на 512 МБ:** поставьте в `.env` `MAX_ATTACHMENT_MB=25`. Юнит имеет лимит `MemoryMax=300M` / `CPUQuota=25%` — бот физически не сможет задеть соседний VPN-сервис.

```bash
journalctl -u mailbot -f   # логи
systemctl restart mailbot  # перезапуск
```

Автообновление при пуше в GitHub: `cd /opt/mail-read-bot && git pull && systemctl restart mailbot`.

## Частые проблемы

### В логах `409 Conflict: terminated by other getUpdates request`

Сначала проверьте, когда он появился:

- **Только в первые ~2 минуты после старта** (обычно через 3–5 секунд) — это наложение при деплое: Render поднял новый контейнер, а старый ещё ~10 секунд жив и продолжает опрашивать Telegram. Бот пишет это как `WARNING` со словом «наложение», всё проходит само, делать ничего не нужно. С недавних пор бот вдобавок выдерживает паузу 8–15 с перед первым опросом — чтобы вообще не пересекаться со старым контейнером.
- **Повторяется и позже** — тогда это настоящий второй экземпляр: бот пишет `ERROR`, а в чат раз в 6 часов уходит предупреждение «Конфликт обновлений (409)». С этим токеном Telegram опрашивает кто-то ещё: VPS, другой хостинг (Koyeb/Railway), забытый локальный запуск. Пока живы оба, команды `/check` и `/status` срабатывают через раз, а письма могут приходить дважды.

Проверить себя: `/status` показывает **счётчик 409-конфликтов** и **аптайм экземпляра** — если счётчик растёт на глазах, а аптайм большой, ищите лишний экземпляр:

```bash
systemctl status mailbot     # на VPS
systemctl disable --now mailbot
```

Бот с одним токеном должен работать **ровно в одном месте**. Если второй экземпляр — это Render, удалите/остановите его сервис. Аптайм в `/status` ещё полезен сам по себе: маленький аптайм при живом сервисе = Render перезапускал контейнер (сон free-тарифа или OOM).

### Бот молчит на бесплатном Render
Free-инстанс Render засыпает через ~15 минут без **входящих HTTP-запросов**, а боту они вообще не приходят — значит, он уснёт почти сразу. Варианты: пинговать `https://<ваш-сервис>.onrender.com` каждые 10–14 минут любым бесплатным монитором (health-endpoint для этого и существует), перейти на платный инстанс или держать бота на VPS (рекомендуется: VPS ещё и дотянется до корпоративного IMAP).

### Видит ли хостинг вашу почту? `/diag`
Откройте `https://<ваш-сервис>.onrender.com/diag` — бот проверит DNS/TCP/TLS до IMAP-сервера **изнутри контейнера** и честно ответит:

- `TCP+TLS …: OK … почта доступна с этого хостинга` → проблема не в сети (смотрите логин/пароль/папку);
- `TCP …: FAIL … timed out` → с этого хостинга порт 993 фильтруется: Render не сможет читать почту, нужен VPS в РФ (или просите админов @fa.ru разрешить IP хостинга).

Регион Render выбирается **только при создании** сервиса и потом не меняется: бесплатный по умолчанию — Oregon (США). Если диагностика показала таймаут, попробуйте пересоздать сервис с регионом **Frankfurt** — но сначала проверьте блокировку через `/diag`, чтобы не делать работу дважды. Если в переменных задан `DIAG_KEY`, адрес диагностики — `/diag?key=<значение>`.

### Mail.ru / Yandex из облака: TCP-таймаут в `/diag`
Ящики **@fa.ru и @edu.fa.ru обслуживает Mail.ru для бизнеса** (MX-запись домена — `emx.mail.ru`), поэтому правильный сервер для них — `imap.mail.ru`, а не `mx.fa.ru` (тот IMAP не обслуживает). Всё описанное ниже относится к ним в полной мере.

Почта Mail.ru агрессивно защищается от автоматических подключений: при частых
обращениях с одного IP (особенно из дата-центров) сервер просто перестаёт
отвечать — в `/diag` видно `TCP …: FAIL … TimeoutError`, при этом ящик в
веб-версии работает, а логин/пароль верные. Что делать:

1. `CHECK_INTERVAL=300` (не меньше). Опрос каждые 30 секунд — прямой путь к блокировке.
2. Убедитесь, что в Mail.ru включён IMAP и создан **пароль для внешних приложений**
   (Настройки → Безопасность → Пароли для внешних приложений) — обычный пароль
   для сторонних клиентов не подойдёт.
3. Если блокировка уже случилась — подождите (обычно от часа до суток), затем
   перезапустите сервис и проверьте `/diag` снова.
4. В боте есть автопауза: после двух сбоев подряд таймерные проверки сами
   замедляются (2 → 4 → 8 → 16 → 30 минут), чтобы не продлевать блокировку.
   Ручной `/check` работает всегда, состояние видно в `/status`.

### Кнопок нет / старые кнопки
Клавиатура приходит сообщением, поэтому в свежем чате её не видно до первого ответа бота: отправьте `/start`. Если кнопки «залипли» на телефоне после смены набора — в Telegram нажмите значок клавиатуры (или перезапустите чат); бот пересоздаёт кнопки при каждом `/start` и `/help`.

### Токен бота засветился в логах
`requests` подставляет полный URL (`bot<TOKEN>/...`) в текст сетевых ошибок. С последнего коммита такие строки вычищаются (`_redact`), но **старые логи уже содержат токен** — в @BotFather: `/revoke` → новый токен → обновите `TG_BOT_TOKEN` в переменных окружения (и на VPS тоже).

### «Проверка уже идёт, пропуск» и долгие проверки
Если IMAP недоступен (хостинг за границей, корпоративная почта отвечает только российским адресам, порт закрыт), проверка висит ~64 с на таймаутах, а таймерные проверки пропускаются. Посмотрите, чем закончилась стартовая проверка (`IMAP connect failed (timed out)` → вторая попытка → ошибка). Если `mx.fa.ru` с этого хостинга недоступен — переносите бота туда, откуда он доступен.

## Важно

- Файл `.env` содержит пароль — **никогда не коммитьте и не передавайте никому** (уже в `.gitignore`).
- После сброса/переустановки телефона бот работает как обычно — он вообще не зависит от App Store.
